## 2. In-Depth Blocker Analysis & Evidence

### Blocker 1: Student Password Compatibility (Status: UNVERIFIED)

#### Complete Read/Write Code Trace
1. **Reads:**
   - `verify_legacy_login`: Queries `users.password`, `student_credentials_vault.pdf_password`, and `student_credentials_vault.excel_password`.
   - **REST API:** `SELECT password FROM users` is **BLOCKED** (`HTTP 401`) — verified live.
2. **Writes:**
   - `admin_update_user_password`: Updates `users.password` and `auth.users.encrypted_password`.
   - Seed migrations: Only ran during initial setup.
   - Bulk migration (`20261017_security_hardening.sql` Section 2): `UPDATE public.users SET password = password`.

#### Static Analysis of Trigger & Edge Cases
- **Prefix Guard:** `LEFT(NEW.password, 3) NOT IN ('$2a', '$2b', '$2x', '$2y')`. Standard bcrypt hashes generated by PostgreSQL `extensions.crypt(..., gen_salt('bf', 10))` produce `$2a$10$...`. The prefix matches and skips re-hashing. Prevents double hashing.
- **Plaintext Passwords:** Representative passwords like `#eu7R7kM`, `fRnp874*`, `h&8TJ8gU` do not start with `$2`. They are successfully intercepted and hashed.
- **NULL & Empty Strings:** Guarded by `IF NEW.password IS NOT NULL AND TRIM(NEW.password) <> ''`. Passing `NULL` passes through unchanged without throwing an exception.
- **Trigger Event Scope:** `BEFORE INSERT OR UPDATE OF password ON public.users`. Updating other columns (e.g. `last_sign_in_at`) **will NOT trigger** password hashing.
- **Admin Password Reset Harmony:** In `admin_update_user_password`, the function pre-hashes with `crypt()` into `$2a$10$...`. When the `UPDATE users` statement executes, the trigger inspects the value, sees `$2a`, and skips. No conflict.
- **Vault Fallback:** The migration defers vault hashing. The vault keeps plaintext passwords, and `verify_legacy_login` path B checks both bcrypt and plaintext.

#### Why it remains UNVERIFIED
Under strict zero-breakage instructions:
- We cannot execute SQL against production.
- No Supabase branch/staging environment was provided to run a physical `crypt()` against real accounts.
- Therefore, we cannot mark this as PASS until at least one test account is verified post-hash.

### Blocker 2: Server-Side Session Revocation (Status: READY)

#### Request Path Trace
```
Student Browser (localStorage.getItem('gradely_session_token'))
       │
       ▼
Supabase RPC get_my_attendance(p_session_token) / get_my_grades(p_session_token)
       │
       ├─► 1. Check auth.uid() (Admins or Supabase Auth students)
       │
       ├─► 2. Check student_sessions WHERE token = TRIM(p_session_token) AND expires_at > now()
       │
       └─► 3. If no student_id resolved ──► RAISE EXCEPTION 'Unauthorized' (42501)
```

#### Executed Live Probe Evidence
- Empty token to `get_my_attendance`: **Rejected (`HTTP 401`)**
- Empty token to `get_my_grades`: **Rejected (`HTTP 401`)**
- Fake 64-character hex token to `get_my_attendance`: **Rejected (`HTTP 401`)**
- Fake 64-character hex token to `get_my_grades`: **Rejected (`HTTP 401`)**
- Direct REST query to `student_sessions`: **Blocked (`HTTP 401`)**

#### Revocation Security Guarantees
- `revoke_student_session(p_session_token text)`:
  - Deletes `FROM public.student_sessions WHERE token = v_clean_token`.
  - Does NOT take a `p_user_id` argument — eliminating Insecure Direct Object References (IDOR).
  - 256-bit entropy prevents brute-force token deletion.
  - Revoking immediately invalidates subsequent calls to `get_my_attendance` and `get_my_grades` because `student_sessions` will no longer contain the token.
- `App.jsx` integration:
  - Uses `Promise.race()` with a 3000ms timeout. If network fails, client logout proceeds safely without hanging.

### Blocker 3: StudentDashboard Direct-Table Fallback (Status: PASS)

#### Inspection of Fallback Queries in `StudentDashboard.jsx` (Lines 330–358)
```javascript
if (!attData || attData.length === 0) {
  const { data: attDirect } = await supabase
    .from('attendance')
    .select('subject_id, week_number, status, created_at')
    .eq('student_id', user.user_id)
    .order('week_number', { ascending: true });
  if (Array.isArray(attDirect) && attDirect.length > 0) attData = attDirect;
}
```

#### Authorization & RLS Evaluation
1. **Can an attacker bypass token authorization via this fallback?**
   - **NO.** Direct access to `public.attendance` and `public.grades` by anonymous callers is **100% REVOKED**:
     - `REVOKE ALL ON TABLE public.attendance FROM anon;` (Migration `20261016`, line 605)
     - `REVOKE ALL ON TABLE public.grades FROM anon;` (Migration `20261016`, line 606)
   - Tested live via REST API: `GET /rest/v1/attendance` returns **`HTTP 401`**.
2. **Can a student modify `user.user_id` in localStorage to read another student's data?**
   - **NO.** For anonymous/legacy students, `auth.uid()` is `NULL`. The RLS policy evaluates:
     `student_id IN (SELECT user_id FROM users WHERE auth_id = auth.uid())`
     When `auth.uid()` is NULL, the subquery returns 0 rows. The RLS filter blocks all rows.
   - For authenticated staff (TAs/Admins), RLS verifies their server-issued JWT, ignoring client tampering.
3. **Flaw identified:** When a student legitimately has 0 attendance records (e.g. start of term), `attData.length === 0` triggers an unnecessary direct query that returns a 401 error in browser console.
4. **Smallest Safe Fix:** In `StudentDashboard.jsx`, guard the fallback so it only triggers if the RPC returned an error and no session token exists:
```javascript
// Minimal safe replacement in StudentDashboard.jsx:
if (attErr && !sessionToken && (!attData || attData.length === 0)) { ... }
```

### Blocker 4: Rate Limiting & Super-Admin MFA (Status: PARTIAL)

#### Honest Technical Assessment of Rate Limiting
- **Current State:** Lockout after 10 failed attempts for 15 minutes, keyed strictly on `user_id`.
- **Proposed in `20261017`:** Threshold raised to 15, lockout duration reduced to 10 minutes.
- **Honest Truth:** **Raising from 10 to 15 DOES NOT solve Targeted Account Lockout DoS.** An attacker with a curl script can send 15 requests in under 2 seconds and lock out a student.
- **Why pure SQL cannot solve this:** A PostgreSQL function cannot distinguish the attacker's IP from the student's IP without relying on spoofable client headers.
- **Proper Architectural Solution:** Keep `login_attempts` as a secondary defense, but implement IP-based rate limiting at the Edge (Cloudflare Rate Limiting or Supabase Kong: max 20 attempts/min per IP on `verify_legacy_login`).

#### Super-Admin MFA Assessment
- **Current State:** Single-factor authentication (email + password).
- **Custom PIN/2FA:** Fully dropped (`HTTP 404` verified live).
- **Native MFA Status:** UNVERIFIED. Cannot be configured via migration script alone.
- **Safe Rollout Sequence to Prevent Lockout:**
  1. Super Admin logs into Supabase Dashboard.
  2. Navigates to **Authentication → Providers / MFA → Enable TOTP**.
  3. Super Admin logs into Gradely frontend, goes to Settings, calls `supabase.auth.mfa.enroll({ factorType: 'totp' })`.
  4. Scans QR code, verifies TOTP code via `supabase.auth.mfa.challenge()` and `verify()`.
  5. Only after verification is successful is MFA marked active.
  6. **DO NOT** enforce `auth.jwt() ->> 'aal' = 'aal2'` in database triggers until enrollment has been verified.

### Recovery Procedure
If any student reports login failure post-migration:
```sql
-- 1. Immediately drop the auto-hash trigger to allow unhashed writes
DROP TRIGGER IF EXISTS trg_auto_bcrypt_users_password ON public.users;
DROP FUNCTION IF EXISTS public.trg_fn_auto_bcrypt_password();

-- 2. Restore verify_legacy_login to check vault fallback unconditionally
-- (The vault has NOT been modified or deleted, so all original passwords remain accessible)
```
Students whose passwords were converted to bcrypt will still be verified via the bcrypt path in `verify_legacy_login`. Students with vault entries can still log in via the vault fallback. Zero data loss.
